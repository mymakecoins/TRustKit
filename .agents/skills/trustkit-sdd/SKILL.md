# Thin Skill Declarativa: TRustKit SDD (v4.2)

Esta skill orquestra o ciclo de vida do SDD delegando todas as validacoes deterministicas, scaffolding de prompt com fatiamento de contexto, linter de especificacao, isolamento de Worktrees, fiscalizacao de TDD, resolucao contextual de proximos passos e transicoes de Gates ao binario nativo `trustkit` (ou pelo alias `tk` oficial e equivalente). Todos os comandos documentados abaixo podem ser invocados indistintamente via `trustkit` ou `tk` (ex: `tk status`, `tk wave run`, `tk task test`, `tk doctor`).

## Invariantes Obrigatorios

1. Proibicao absoluta de emojis ou icones Unicode em qualquer arquivo ou commit.
2. Proibicao absoluta de trailers de autoria IA (ex: Co-Authored-By, Generated by).
3. Toda mutacao de estado e validacao de invariantes deve ser executada pelo binario `trustkit`.
4. A especificacao no Gate 1 deve ser formulada via comandos nativos ou ferramentas MCP, validada continuamente via `trustkit spec lint` e congelada no Gate 2 via `trustkit spec lock`.
5. Os testes do Gate 4 devem seguir estritamente o ciclo TDD: RED comprovado antes de GREEN.
6. Abertura de Pull Request ocorre exclusivamente sob demanda humana explicita.
7. Ao final de cada comando ou turno de interacao, o agente deve obrigatoriamente ler o array `next_steps` do JSON retornado pelo binario (ou o bloco `NEXT STEP:` da saida ASCII) e apresentar ao usuario a orientacao explicita do proximo passo.

## Protocolo Obrigatorio de Orientacao de Proximo Passo (Next-Step Guidance)

Todo comando do binario `trustkit` emite deterministica e contextualmente as proximas acoes recomendadas para o ciclo ativo:
- No modo `--json`: por meio do array `next_steps`, contendo objetos com `priority` (`PRIMARY`, `SECONDARY`, `OPTIONAL`), `target_gate`, `command` e `description`.
- No modo ASCII: por meio do rodape padronizado `NEXT STEP:`.

Sempre que concluir a execucao de um comando ou etapa do SDD, o agente **DEVE** encerrar sua resposta ao usuario com o seguinte bloco padronizado (sem emojis):

```text
RESUMO DO GATE ATUAL:
- Gate / Status: <Gate atual e veredito retornado pelo trustkit>
- Artefatos afetados: <Arquivos criados, validados ou selados>

PROXIMO PASSO RECOMENDADO:
- [PRIMARY] (<target_gate>) `<command>`
  <description>
- [SECONDARY/OPTIONAL] (<target_gate>) `<command>` (quando aplicavel)
  <description>
```

Caso o usuario retome uma sessao sem saber o estado atual, execute `trustkit status --json` para inspecionar o ciclo, as tarefas pendentes na onda e apresentar o `next_steps` calculado pelo resolvedor contextual.

## Jornada dos Gates

### Modo Autonomo Unificado (Gates 0 ao 6 - v2.2)
Para execucao 100% autonoma de ponta a ponta sem intervencoes manuais. O motor v2.2 atomiza tarefas a partir da especificacao ou issue se `tasks/` nao existir, dispara disjuntor `EmptyTaskBacklogFault` para especificacoes vazias, sintetiza scaffolds RED compilaveis e realiza merge seguro:
```bash
# Execucao autonoma a partir de issue remota
trustkit auto --issue <ISSUE_ID> [--target develop] [--runtime auto|pty|native] --json

# Execucao autonoma a partir de especificacao local
trustkit auto --spec <CAMINHO_SPEC> [--target develop] [--runtime auto|pty|native] --json
```

### Gate 0: Inicializacao do Ciclo
Execute a inicializacao para validar identidade, branches e registrar a sessao:
```bash
trustkit init --issue <ISSUE_ID> [--from-prd <CAMINHO_PRD>] [--milestone <CAMINHO_MILESTONE>] --json
```

### Gate 1: Formulacao e Validacao da Especificacao (Nativa)
Gere o prompt contextualizado e o esqueleto formal da especificacao a partir de uma ideia em linguagem natural:
```bash
# Gera o prompt estruturado com fatiamento de contexto AST e busca FTS5 na memoria viva
trustkit spec prompt --idea "<DESCRICAO_DA_FEATURE>" --context-hops 2 --json
```

Em clientes MCP (Claude Code, Antigravity, IDEs), as ferramentas equivalentes estao disponiveis:
- `trustkit_spec_template`: gera o esqueleto do spec.md com regras constitucionais.
- `trustkit_spec_context`: recupera artigos da wiki e fatias AST de codigo relevante.
- `trustkit_spec_lint`: executa linter estatico imediato (< 3ms) com diagnosticos estruturados.

Valide continuamente o arquivo `spec.md` durante a redacao para auto-correcao pre-lock:
```bash
trustkit spec lint [--file <CAMINHO_SPEC>] --json
```

### Gate 2: Congelamento Criptografico (Spec Lock)
Apos a aprovacao pelo linter com veredito CleanPass, congele a especificacao com selo BLAKE3:
```bash
trustkit spec lock [--spec <CAMINHO_SPEC>] --json
```

### Gate 3: Tarefas Atomicas e Planejamento de Ondas
Elabore as tarefas atomicas em `tasks/TASK-NNN.md` (ou permita que `trustkit auto` atomize a partir da Matriz de Rastreabilidade ou da Issue) e planeje o DAG de ondas paralelas:
```bash
trustkit wave plan --json
```
Nota de Governanca: se o backlog de tarefas atomicas resultar vazio no Gate 3, o disjuntor `EmptyTaskBacklogFault` bloqueia imediatamente o ciclo com exit code 1.

### Gate 4: Execucao em Git Worktrees, Multiplexacao de Terminais e TDD Estrito
Execute as tarefas da onda com isolamento de worktree, runtime multiplexado (multiplexador PTY ou nativo) e garanta as fases TDD:
```bash
# Executa a onda com isolamento de worktree e runtime de terminais (auto, pty, native)
trustkit wave run --wave <WAVE_INDEX> [--runtime auto|pty|native] [--agent-cmd "<cmd>"] --json

# Autoria RED: redigir e adicionar a assercao do teste falhando em target_test_file antes de validar a fase RED

# Registra a fase RED (falha obrigatoria comprovada por assercao de dominio, rejeitando ZeroFilteredTests e CompilationFailure)
trustkit task test <TASK_ID> --phase red --json

# Implementa o codigo de producao minimo para satisfazer a especificacao

# Registra a fase GREEN (sucesso obrigatorio comprovado)
trustkit task test <TASK_ID> --phase green --json

# Realiza revisao semantica estrita de codigo (Dual-Axis: Standards/Smells e Spec Compliance)
trustkit task review <TASK_ID> [--effort high|medium|low] --json

# Conclui a tarefa atomica
trustkit task complete <TASK_ID> --json
```

Ferramentas MCP de monitoramento e controle de terminais de agentes estao disponiveis:
- `trustkit_wave_status`: consulta status agregado de tarefas e terminais da onda.
- `trustkit_terminal_inspect`: inspeciona estado semantico e buffer recente sanitizado da tarefa.
- `trustkit_terminal_send`: envia entradas ao stdin do terminal para destravar agentes em estado Blocked.

### Gate 5: Gauntlet V2 (Auditoria AST e Swarm de Criticos)
Execute a auditoria lexica/AST da Camada 0 e os criticos da Camada 1:
```bash
# Camada 0: Scanner lexico, invariantes, ausencia de emojis e integridade de assercoes
trustkit gauntlet ast-audit --json

# Camada 1: Swarm de criticos concorrentes e guardiao de evidencias visuais
trustkit gauntlet run --json

# Diagnostico caso o disjuntor (Circuit Breaker) seja acionado apos falhas
trustkit doctor --json
```

### Gate 6: Certificacao, Merge e Pull Request Sob Demanda
Gere o relatorio oficial de certificacao, faca o merge e abra o PR sob demanda:
```bash
# Consolida evidencias e gera gauntlet-report.md
trustkit done --json

# Executa merge deterministico para a branch alvo
trustkit merge --target develop --json

# Abre Pull Request no GitHub Projects (apenas sob demanda do usuario)
trustkit pr --target develop --json
```

## Codigos de Saida Semanticos (POSIX Exit Codes)

| Codigo | Categoria | Descricao |
|---|---|---|
| 0 | CleanPass | Operacao concluida com sucesso e aprovada em todos os gates. |
| 1 | InfrastructureBoundaryFault | Falha de I/O, banco de dados SQLite WAL, Git ou rede. |
| 2 | SpecOrTraceabilityIncomplete | Falha de sintaxe Mermaid/Gherkin ou spec com violacao estrutural. |
| 3 | TddLifecycleViolation | Tentativa de GREEN sem RED previo, ou gap de rastreabilidade. |
| 4 | AstIntegrityOrInvariantViolation | Emojis detectados, trailers de IA ou ciclos no grafo DAG. |
| 5 | CriticSwarmOrPlaywrightFailed | Reprovacao por critico do Gauntlet ou falha em teste E2E. |
| 6 | CircuitBreakerTripped | Disjuntor acionado apos 5 falhas consecutivas no Gauntlet. |
