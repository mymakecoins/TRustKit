Manual Oficial de Uso do TRustKit

Guia operacional completo para desenvolvedores, arquitetos, lideres tecnicos e operadores agenticos. Aprenda a orquestrar os 7 Gates do Spec-Driven Development (SDD), isolamento em Git Worktrees, revisao em dois eixos (Dual-Axis Review), governanca formal de fechamento com close, auditoria sintatica de Camada 0 e certificacao com Event Sourcing no SQLite WAL, utilizando os binarios trustkit e o alias conciso tk.

Versao: 1.2.0 Binarios: trustkit / tk Linguagem: Rust Nativo (6 Crates) Latencia AST: < 3ms Invariantes: 16 Regras Ferramentas MCP: 23 Tools

1. Visao Geral & Boas-Vindas

O TRustKit e uma plataforma deterministica voltada para fluxos de desenvolvimento orientados a especificacoes (Spec-Driven Development — SDD). Construido em Rust de alto rendimento, ele substitui rotinas interpretadas lentas por validacoes compiladas ultrarrapidas que executam em 1 a 3 milissegundos.

Velocidade Instantanea < 3ms

Validacao sintatica em microssegundos com parsers AST nativos do Tree-Sitter, sem cold-starts de runtime.

Zero Alucinacao Deterministico

Verificacao mecanica de fechamento de matrizes, integridade de testes e regras sintaticas sem depender de probabilidade de LLMs.

Paralelismo Seguro Git Worktrees

Execucao simultanea de tarefas em arvores de trabalho isoladas via Copy-on-Write (reflink), prevenindo corrupcao de indice.

Auditoria Imutavel SQLite WAL

Persistencia transacional imutavel (.trustkit/state.db) com selos criptograficos BLAKE3 de cada transicao de estado.

1.1 O Binario Principal e o Alias tk

O TRustKit disponibiliza dois pontos de entrada compilados nativamente com paridade contratual estrita de 100%: o comando principal trustkit e o comando curto tk.

O mecanismo de resolucao dinamica de argv0 garante que as mensagens de ajuda, exemplos e codigos de diagnostico reflitam exatamente o nome com o qual o comando foi invocado. Assim, qualquer instrucao documentada como trustkit <comando> pode ser executada indistintamente como tk <comando>.

Exemplos de Paridade Total
# Ambas as chamadas executam exatamente a mesma logica e compartilham o mesmo estado:
trustkit status
tk status

trustkit wave run --wave 1
tk wave run --wave 1

trustkit close
tk close

1.2 Arquitetura Dual-Audience e Orientacao de Proximo Passo

Para assegurar que agentes autonomos de IA e desenvolvedores humanos operem em perfeita sintonia, todos os comandos do TRustKit seguem o padrao Dual-Audience Presenter:

  • Para Humanos (Terminal TTY): Respostas estruturadas em texto legivel com prefixos claros ([PASS], [FAIL], [INFO]) e o bloco NEXT STEP: no rodape, indicando explicitamente a proxima acao priorizada ([PRIMARY], [SECONDARY], [OPTIONAL]).
  • Para Agentes (Flag --json): Carga JSON estritamente livre de valores nulos (null-free), contendo o array next_steps resolvido pelo NextStepResolver com command, rationale e priority.

1.3 O Paradigma Hybrid Rust Core + Thin Skill

O TRustKit utiliza uma arquitetura hibrida pioneira:

  • Native Rust Core (trustkit / tk): O motor compilado que executa mutacoes de estado, criptografia BLAKE3, parsing AST com Tree-Sitter e isolamento de Git Worktrees.
  • Thin Skill Layer (.agents/skills/trustkit-sdd): Instrucoes enxutas em Markdown que residem no contexto do assistente agêntico para guiar decisoes sem poluir a janela de contexto nem invalidar o cache KV.

1.4 Principios Constitucionais de Governanca

Principio Regra Constitucional Descricao Operacional
Principio I Isolamento Hexagonal Estrito O crate trustkit-core contem apenas regras de dominio puras (std), sem dependencias externas de banco ou rede.
Principio II Proibicao Absoluta de NULL Todas as interfaces, APIs e cargas JSON rejeitam nulos, adotando objetos de Caso Especial (Null Object Pattern).
Principio III Ciclo TDD Rigoroso Nenhuma tarefa e aprovada sem a comprovacao fisica de falha (fase RED) antes da implementacao (fase GREEN).
Principio IV Politica Zero Panic O binario captura falhas e as converte em codigos de erro semanticos POSIX, sem abortos abruptos em producao.
Principio V Pull Requests Sob Demanda A abertura de PRs para a branch de destino e uma acao exclusivamente humana via comando trustkit pr ou tk pr.
Principio VI Codigo Limpo e Modular (< 250 LOC) Modulos focados com alta coesao e limites de linhas rigidos.
Principio VII Zero Emojis e Zero AI Trailers Proibicao absoluta de grafismos, icones de emoji e metadados de autoria gerados por IA em commits e codigos.

2. Primeiros Passos & Instalacao

Configure e verifique o funcionamento dos binarios trustkit e tk antes de iniciar suas demandas.

2.1 Compilacao e Instalacao

Terminal (Bash) 
# Compilar o workspace em modo release (gera os binarios trustkit e tk)
cargo build --workspace --release

# Opcional: criar atalhos globais no sistema (/usr/local/bin)
sudo ln -sf "$(pwd)/target/release/trustkit" /usr/local/bin/trustkit

# Checar versao instalada de ambos
trustkit --version

2.3 Modos de Operacao: Humano vs Agente

O TRustKit suporta nativamente dois formatos de saida ergonomicos:

  • Modo Humano (Padrao): Apresenta tabelas limpas, texto legivel, prefixos padronizados como [PASS], [FAIL], [GATE-0] a [GATE-6] e o rodape contextual NEXT STEP: indicando os proximos comandos priorizados ([PRIMARY], [SECONDARY], [OPTIONAL]).
  • Modo Agente (Flag --json ou TRUSTKIT_AGENT_MODE=1): Retorna dados em JSON minificado, sem formatacao ANSI, sem valores nulos (null) e enriquecidos com o array next_steps calculado pelo NextStepResolver (priority, target_gate, command e description).

2.5 Guia de Adocao: Novo Projeto vs Projeto em Andamento

O comando trustkit init (ou tk init) inspeciona o ambiente, gerencia o .gitignore sem quebrar exclusoes existentes, provisiona o template trustkit.toml, inicializa o banco SQLite WAL e monta a infraestrutura do ciclo de forma transparente.

Cenario A: Projeto Novo Greenfield

Repositorio vazio, sem codigo pre-existente. Apos configurar o Git e o remote, o comando unico cuida de todo o scaffolding.

Cenario B: Projeto Existente Brownfield

Repositorio com codigo e historico ativos. O TRustKit anexa regras ao .gitignore existente sem sobrescrever exclusoes anteriores, mapeia o grafo estrutural e diagnostica God Nodes.

Cenario A: Configurando o TRustKit em Projeto Novo

Passo 1: Preparacao do Repositorio Git 
mkdir meu-novo-sistema && cd meu-novo-sistema
git init -b develop
git remote add origin git@github.com:organizacao/meu-novo-sistema.git
git commit --allow-empty -m "chore: initial repository bootstrap"
Passo 2: Inicializacao do SDD via tk 
# Se vinculado a uma issue do GitHub Projects:
tk init --issue 1

# Ou para ciclo puramente local (desconectado):
tk init
O que o comando init realiza automaticamente:
  • Gerencia o .gitignore: Anexa as exclusoes essenciais (.trustkit/state.db*, .trustkit/worktrees/, .trustkit/audits/ e !.trustkit/wiki/) preservando regras ja existentes.
  • Gera o trustkit.toml: Cria as configuracoes de governanca do Gauntlet caso ausentes.
  • Provisiona a infraestrutura: Cria .trustkit/, inicializa o banco SQLite WAL com migrations e cria o diretorio de especificacoes docs/specs/<ciclo>/.

3. Guia Operacional Passo a Passo (Os 7 Gates do SDD)

Conheca o roteiro pratico e deterministico para conceber, implementar, auditar e homologar entregas com qualidade total.

Gate 0: Inicializacao do Ciclo e Setup de Contexto

Prepara a arvore de trabalho, valida a conta do GitHub e registra a sessao transacional no banco SQLite WAL.

Iniciar ciclo com Issue vinculada 
# Inicializa o ciclo vinculado a issue 45
tk init --issue 45

# Ou inicializa importando regras de um documento PRD funcional
tk init --issue 45 --from-prd docs/PRD_TRustKit.md

Acoes executadas automaticamente pelo comando:

  1. Valida credenciais do GitHub CLI e assegura que a conta corporativa esteja ativa.
  2. Inspeciona o Git e protege arquivos modificados pre-existentes contra perda acidental.
  3. Cria a pasta isolada de especificacao: docs/specs/issue-45-AAAAMMDDHHMM/.
  4. Transiciona o card para 'In progress' no GitHub Projects.
  5. Abre a sessao auditavel no SQLite WAL (.trustkit/state.db).

Gates 1 & 2: Especificacao V2, Glossario Ubiquo e Selo Criptografico BLAKE3

Garante que todos os requisitos funcionais, fluxos de tela e termos de negocio estejam blindados antes de programar.

Passo 1: Gerar prompt e esqueleto da Spec com termos de negocio 
# Injeta automaticamente o Glossario Ubiquo e contexto estrutural AST no prompt da spec
tk spec prompt --idea "Autenticacao MFA via TOTP com codigos de recuperacao" --budget 4000
Passo 2: Executar Linter Estatico Pre-Lock (< 3ms) 
# Valida sintaxe Gherkin, diagramas Mermaid, matriz e termos canonicos (regra SPEC-008)
tk spec lint
Passo 3: Congelar a especificacao (Gate 2) com Selo BLAKE3 
tk spec lock
Fechamento Estrito da Matriz de Rastreabilidade e Glossario Ubiquo
O comando spec lock valida matematicamente que cada Regra de Negocio (RN) possui correspondencia com um Requisito Funcional (RF), uma Tarefa (TASK), um Teste E2E e uma captura de tela (Screenshot). Alem disso, verifica se termos ambíguos ou rejeitados pelo glossario foram eliminados. Se houver regras orfas ou violacoes lexicais, o congelamento e barrado imediatamente.

Gate 3: Decomposicao Atomica e Topologia em Ondas (DAG Expand-Contract)

Valida as tarefas atomicas em tasks/TASK-NNN.md, calcula o grafo aciclico direcionado (DAG) e analisa o raio de explosao (Blast Radius).

Compilar DAG e Planejar Ondas 
tk wave plan

O planejador analisa dependencias declaradas e assegura que tarefas que alterem os mesmos arquivos fiquem em ondas distintas. A topologia Expand-Contract organiza tarefas de introducao de novos modelos em ondas de expansao antes de migrar consumidores legados.

Inspecionar Ondas e Status de Tarefas (Inspecao Passiva: tk wave view) 
# Inspecao visual formatada no terminal
tk wave view

# Ou exportacao JSON deterministica estritamente livre de null:
tk wave view --json

O comando wave view consulta deterministicamente o ciclo ativo e suas tarefas persistidas sem reprocessar o planejamento, exibindo a distribuicao de ondas com status TDD e dependencias de cada tarefa atomica.

Gate 4: Execucao em Git Worktrees, TDD Mecanico e Dual-Axis Review

Implementa cada tarefa em arvores isoladas, com notificacao estruturada de criacao, exigencia de comprovacao de falha (RED) e revisao de codigo em dois eixos.

1. Despachar onda de trabalho (provisiona Git Worktrees isolados) 
tk wave run --wave 1
Notificacao de Provisionamento de Worktree (Pure ASCII no TTY)
[INFO] Branch 'worktree/TASK-001' criada com sucesso.
[INFO] Checkout realizado no diretorio isolado: .trustkit/worktrees/TASK-001
[INFO] Branch ativa do repositorio raiz preservada: 'develop'
[PASS] Wave 1 executed: 2/2 tasks passed in 48ms
2. Comprovar Fase RED Obrigatoria (Falha fisica do teste de dominio) 
# Exige teste compilavel que falhe exclusivamente por assercao de dominio
tk task test TASK-001 --phase red
3. Implementar codigo e comprovar Fase GREEN (Sucesso do teste) 
tk task test TASK-001 --phase green
4. Revisao de Codigo em Dois Eixos (Dual-Axis Review - Fase REFACTOR) 
# Avalia Eixo 1 (Scope Creep & Spec Compliance) e Eixo 2 (Fowler Smells via AST)
tk task review TASK-001 --effort medium
Exemplo de Relatorio Dual-Axis Review
=== DUAL-AXIS CODE REVIEW: TASK-001 ===
Overall Verdict: PASS

[Standards & Fowler Smells]
Verdict: PASS (findings: 0)
  (no findings)

[Spec Compliance & Scope Creep]
Verdict: PASS (findings: 0)
  (no findings)
5. Homologar e Concluir a Tarefa (Blindagem Estrita de Commit - RN-001) 
# Bloqueia se o worktree contiver alteracoes pendentes (uncommitted changes)
tk task complete TASK-001
Blindagem de Integridade da Working Tree (RN-001)
O comando task complete impede que uma tarefa seja concluida caso a arvore de trabalho correspondente esteja suja (com arquivos modificados ou novos nao commitados, desconsiderando pastas temporarias como target/ ou node_modules/). O desenvolvedor ou agente deve registrar o commit de implementacao antes de homologar a tarefa.

Gate 5: Gauntlet Loop V2 e Auditoria de Seguranca

Auditoria profunda dividida em duas camadas deterministas: Camada 0 sintatica via AST em microssegundos e Camada 1 com swarm de criticos e Playwright.

Camada 0: Inspecao AST Instantanea (< 3ms) 
# Audita anti-cheat de assercoes, zero emojis e ausencia de trailers de IA
tk gauntlet ast-audit
Camada 1: Gauntlet Swarm, Playwright E2E e Security Review 
# Execucao padrao com pergunta interativa de seguranca
tk gauntlet run

# Ou forcando explicitamente a revisao de seguranca do diff
tk gauntlet run --security-review

# Ou dispensando temporariamente a revisao de seguranca
tk gauntlet run --skip-security-review
Disjuntor de Seguranca (Circuit Breaker) e Merge Danger Door
Se o Gauntlet registrar 5 reprovacoes consecutivas, o disjuntor e acionado para prevenir loops infinitos de correcao. Alem disso, o modulo verifica preventivamente a arvore de merge (Merge Danger Door) para antecipar conflitos antes da branch alvo. Para investigar e destravar, execute tk doctor.

Gate 6: Certificacao Oficial, Fechamento de Ciclo (close) e Pull Request

Emite o dossie de evidencias oficial, fecha formalmente o ciclo transicionando o board para ReadyForTest e prepara a integracao.

Passo 1: Certificar e gerar o relatorio gauntlet-report.md 
# Consolida o dossie formal e gera o comentario oficial na issue do GitHub
tk done
Passo 2: Fechar Formalmente o Ciclo Ativo (Comando Oficial: close) 
# Valida a certificacao do ciclo, fecha o estado e transiciona a issue para 'ReadyForTest'
tk close
Saida do Fechamento Formal (tk close)
[PASS] Cycle 'issue-45-202611041030' successfully closed.
[INFO] GitHub Projects board column transitioned to: ReadyForTest
[INFO] State recorded in SQLite WAL (.trustkit/state.db).
Passo 3: Abertura de Pull Request (Sob Demanda Humana Explicita) 
# Publica o Pull Request na branch de destino indicada
tk pr --target develop
Aviso de Depreciacao do Antigo Comando merge
O comando trustkit merge foi oficialmente descontinuado e substituido por trustkit close (ou tk close). Caso merge seja invocado, o sistema emitira o aviso: "WARNING: 'trustkit merge' is deprecated and will be removed in a future release. Please adopt 'trustkit close' immediately." Adote close em todos os fluxos.

  • Onda 2 (Regra de negocio / Servicos): TASK-003 (Servico de Autenticacao / Dominio)

3.8 Orquestracao Autonoma de Ponta a Ponta (trustkit auto / tk auto)

O comando unificado trustkit auto (ou tk auto) executa a jornada inteira dos 7 gates (Gate 0 ao Gate 6) de forma 100% autonoma e deterministica, incluindo atomizacao automatica de tarefas, scaffolding TDD, gestao de worktrees com commit obrigatorio e integracao final:

  • Gate 0 (Setup & Init): Inspeciona identidade Git, branches e baseline limpo, inicializando no SQLite WAL.
  • Gate 1 (Spec Lint): Valida o linter nativo AST em microssegundos (sem emojis, Gherkin e matriz fechada).
  • Gate 2 (Spec Lock): Sela a especificacao congelada com hash BLAKE3 criptografico.
  • Gate 3 (Wave Plan & Atomizacao): Atomiza deterministicamente a especificacao se tasks/ nao existir, dispara o disjuntor EmptyTaskBacklogFault se houver zero tarefas e calcula as ondas DAG.
  • Gate 4 (Multi-Wave TDD Loop & Builder Dispatch): Sintetiza testes RED compilaveis, bloqueia filtros vazios (ZeroFilteredTestsFault) e erros de compilacao mascarados na fase RED (CompilationFailureInRedPhaseFault), despacha agentes construtores e comita alteracoes de tarefas em cada worktree antes da homologacao.
  • Gate 5 (Gauntlet V2): Executa auditoria Camada 0 e consolida vereditos dos criticos adversariais, de contrato, estaticos e Playwright.
  • Gate 6 (Certify & Close): Emite gauntlet-report.md, atualiza o card para ReadyForTest e realiza o fechamento formal via close.
A partir de uma issue remota do GitHub 
tk auto --issue 45 --target develop
A partir de um arquivo local de especificacao 
tk auto --spec docs/specs/minha-feature/spec.md --target develop
Modo Agente com saida JSON determinista (livre de null) 
tk auto --spec docs/specs/minha-feature/spec.md --target develop --runtime native --json

4. Recursos Avancados e Modulos Especializados

4.1 Memoria Perene do Projeto (trustkit memory / tk memory)

Gerencia a base de documentacao viva estruturada em Markdown sob .trustkit/wiki/, com indexacao FTS5 BM25, suporte a [[wikilinks]], gestao de Glossario Ubiquo e Triagem de Decisoes de Arquitetura (ADR Check).

Comandos Basicos de Wiki e Memoria
# Buscar documentos por termo semantico ranqueado por BM25
tk memory search "diretrizes de testes" --limit 5

# Ler uma nota de documentacao especifica
tk memory read adrs/adr-002-storage-strategy

# Registrar ou atualizar nota na memoria perene
tk memory write adrs/adr-002-storage-strategy --title "Estrategia de Armazenamento" --tags "adr,storage,sqlite" --content "Decisao de persistencia..."

# Listar todas as notas cadastradas
tk memory list

# Reconstruir deterministicamente o indice SQLite FTS5 e grafo de wikilinks
tk memory rebuild

Gestao de Glossario Ubiquo (Linguagem Canonica de Negocio)

Registra termos canônicos e sinonimos rejeitados em .trustkit/wiki/glossary.md. O linter de especificacoes (regra SPEC-008) utiliza essa base para impedir ambiguidades conceituais.

Comandos do Glossario Ubiquo
# Adicionar ou atualizar termo canonico no glossario
tk memory glossary add --term "SddCycle" --definition "Instancia isolada e auditavel correspondente ao ciclo de vida de uma entrega" --rejected "sprint,task-bundle"

# Listar todos os termos canonicos cadastrados
tk memory glossary list

Triagem de Proposta de ADR (Filtro de 3 Criterios Arquiteturais)

Avalia se uma mudanca tecnica proposta justifica a redacao de um Architectural Decision Record formal: 1) Dificil de reverter (--hard-to-reverse); 2) Surpreendente para novatos (--surprising); 3) Possui tradeoffs genuinos (--tradeoff).

Triagem de ADR
# Avaliar proposta de decisao arquitetural
tk memory adr-check --title "Adocao de SQLite WAL para Persistencia" --context "Persistencia de evidencias de ciclo SDD" --hard-to-reverse --surprising --tradeoff

4.2 Inteligencia de Grafo Estrutural (trustkit graph / tk graph)

Mapeia dependencias sintaticas de codigo (funcoes, imports, structs) e notas wiki com deteccao automatica de componentes hiperacoplados (God Nodes).

Comandos de Grafo
# Construir ou atualizar o grafo estrutural (emite GRAPH_REPORT.md)
tk graph build

# Diagnosticar a saude do grafo e componentes criticos
tk graph health --top-god-nodes 5

# Encontrar menor caminho de chamadas entre dois simbolos via BFS
tk graph path --source "crates/trustkit-core::SddCycle" --target "crates/trustkit-db::SqliteWalRepositoryAdapter"

# Explicar relacoes e dependencias de um componente
tk graph explain --node "crates/trustkit-core/src/entities.rs::SddCycle"

4.3 Fatiamento Cirurgico de Contexto (trustkit context / tk context)

Extrai apenas as assinaturas, interfaces e tipos necessarios para alimentar prompts de IA sem exceder janelas de contexto.

Exemplos de Fatiamento
# Fatiamento classico por arquivo com orcamento de tokens
tk context slice --file crates/trustkit-core/src/lib.rs --budget 500

# Fatiamento multi-hop guiado pelo grafo estrutural (BFS)
tk context slice --file crates/trustkit-core/src/entities.rs --hops 2 --strategy bfs --budget 800

4.4 Protecao Proativa com Fast Hooks (trustkit hook / tk hook)

5. Perguntas Frequentes (FAQ)

Qual e a diferenca entre o binario trustkit e o alias tk?
Nao ha nenhuma diferenca funcional ou semantica. O binario tk e um alias de primeira classe com paridade contratual de 100% com trustkit. Ambos compartilham o mesmo banco de dados (.trustkit/state.db), a mesma maquina de estados e as mesmas regras. Utilize tk para maior concisao e agilidade no terminal.
Por que o comando trustkit close substituiu o antigo trustkit merge?
O comando trustkit close (ou tk close) implementa o use case formal close_cycle, que valida a certificacao previa do Gauntlet (rejeitando fechamento de ciclos nao certificados), atualiza o estado persistido no SQLite WAL e sincroniza automaticamente a coluna do card no GitHub Projects para ReadyForTest. O antigo comando merge foi descontinuado (deprecated) para evitar integracoes acidentais sem validacao completa do board.
Por que recebi o erro "working tree has uncommitted changes (RN-001)" no task complete?
A regra de negocio RN-001 exige integridade total da arvore de trabalho antes da homologacao de qualquer tarefa. Voce nao pode executar task complete com arquivos modificados ou novos nao commitados dentro da worktree (pastas temporarias como target/ e node_modules/ sao ignoradas). Realize o commit das alteracoes da tarefa antes de executar a conclusao.
Como funciona a revisao em dois eixos (Dual-Axis Review) no Gate 4?
Durante a fase REFACTOR (task review), o sistema analisa simultaneamente: Eixo 1 (Spec Compliance): avalia se a tarefa implementou estritamente o que foi contratado ou se introduziu desvios de escopo (Scope Creep); Eixo 2 (Fowler Smells via AST): o Tree-Sitter audita o diff procurando code smells lexicais (Long Function, God Structs, Primitive Obsession, etc.), permitindo overrides especificos configurados pelo repositorio.
Como os agentes de IA consom o array next_steps e os humanos usam o rodape NEXT STEP:?
O TRustKit implementa o padrao Dual-Audience: quando invocado no terminal, renderiza o rodape legivel NEXT STEP: com comandos priorizados ([PRIMARY], [SECONDARY]). Quando executado com a flag --json, inclui o array estruturado next_steps livre de campos nulos. Isso permite que agentes autonomos de IA saibam exatamente qual comando executar a seguir sem necessitar de inferencia probabilistica.
O que acontece se eu precisar alterar uma regra de negocio apos o Gate 2?
Uma vez selada a especificacao, qualquer mudanca manual em spec.md viola a assinatura BLAKE3 e impede novos commits. Para atualizar requisitos, execute uma revisao formal que atualize os hashes e valide a Matriz de Rastreabilidade.
Por que o Pull Request nao abre automaticamente ao final do Gate 6?
A Invariante Constitucional #12 proibe a abertura autonoma de Pull Requests. A decisao de submeter o trabalho para integracao em branches estaveis pertence exclusivamente ao desenvolvedor humano responsavel via comando trustkit pr ou tk pr.

6. Guia de Solucao de Problemas (Troubleshooting)

6.1 Codigos de Saida Semanticos (POSIX)

Codigo Identificador Causa Frequente Acao Recomendada
0 CleanPass Operacao concluida com aprovacao. Avancar para o proximo comando indicado no NEXT STEP:.
1 InfrastructureBoundaryFault Erro de I/O em disco, SQLite WAL, Git ou disjuntor de tarefas vazias (EmptyTaskBacklogFault). Verificar permissoes de escrita, espaco em disco ou revisar itens acionaveis na especificacao.
2 SpecOrTraceabilityIncomplete Spec incompleta, lacuna na matriz ou violacao de glossario ubíquo (SPEC-008). Executar tk spec lint e cobrir regras orfas ou ajustar termos rejeitados.
3 TddLifecycleViolation Tentativa de GREEN sem RED comprovado, filtro vazio (ZeroFilteredTestsFault), erro de compilacao na fase RED (CompilationFailureInRedPhaseFault) ou arvore de trabalho suja (RN-001). Garantir teste compilavel que falhe por assercao de dominio e comitar alteracoes antes de task complete.
4 AstIntegrityOrInvariantViolation Presenca de emojis, trailers de IA no commit ou alteracao indevida de testes protegidos. Executar tk gauntlet ast-audit para identificar e eliminar os grafismos ou trailers.
5 CriticSwarmOrPlaywrightFailed Falha de compilacao no swarm, linter de codigo ou quebra de cenarios Playwright E2E. Inspecionar relatorio de testes e corrigir as falhas funcionais apontadas.
6 CircuitBreakerTripped Disjuntor disparado apos 5 falhas consecutivas ou ativacao do Merge Danger Door. Executar tk doctor para diagnosticar a causa-raiz e seguir os passos de recuperacao.

6.2 Diagnostico com o Assistente Doutor (trustkit doctor / tk doctor)

Caso o ciclo seja bloqueado, o banco SQLite WAL apresente anomalias ou o disjuntor tenha sido acionado, invoque o diagnosticador unificado:

Executar Diagnostico Global
tk doctor

O comando inspeciona a conexao com state.db, a saude dos worktrees ativos, conflitos potenciais na branch alvo e fornece o roteiro de desbloqueio.
