# TRustKit

Motor Determinístico em Rust para Governança de Spec-Driven Development (SDD), Isolamento em Git Worktrees e Gauntlet Loop V2.

"True Rust performance for trusted, spec-driven agentic execution."

---

## 1. Visão Geral

O TRustKit é uma plataforma de governança e execução determinística voltada para fluxos de desenvolvimento orientados a especificações (Spec-Driven Development - SDD) em ambientes com agentes de inteligência artificial (Claude Code, Antigravity, Codex) e desenvolvedores sêniores.

O projeto resolve os gargalos críticos de abordagens puramente declarativas (skills em Markdown) e harnesses legados em linguagens interpretadas (Python/Node.js):
- Redução drástica da latência: substituição de tempos de cold-start de 300ms a 2.000ms por validações nativas em Rust executadas em 1 a 3 milissegundos.
- Eliminação de alucinações de conformidade: validação mecânica de regras sintáticas, integridade de testes e invariantes de projeto sem depender do julgamento probabilístico de LLMs.
- Paralelismo seguro via Git Worktrees: isolamento de múltiplos agentes construtores (builders) em árvores de trabalho independentes com suporte a Copy-on-Write (reflink), prevenindo corrupção de índice e colisões.
- Auditoria imutável via Event Sourcing: persistência transacional em SQLite em modo WAL (`.trustkit/state.db`) com registro auditável de cada transição de estado, saída de comando e hash de artefato.

### O Paradigma Hybrid Rust Core + Thin Skill

O TRustKit adota a arquitetura híbrida:
- Thin Skill Declarativa: uma camada enxuta em Markdown que reside na memória de trabalho do agente orquestrador para orientar a tomada de decisões de produto e design de código sem invalidar o cache de contexto (KV-Cache).
- Native Rust Core: o binário estático `trustkit`, responsável por 100% das mutações de estado, validação de AST, congelamento criptográfico com BLAKE3, orquestração de processos Git e sincronização com o GitHub Projects.

## 2. Invariantes Obrigatórios de Governança

Todas as operações gerenciadas pelo TRustKit respeitam estritamente as regras de integridade do projeto:
1. Proibição absoluta de emojis ou ícones gráficos em qualquer arquivo, documentação, saída de terminal ou commit.
2. Proibição absoluta de trailers de autoria gerados por IA (como `Co-Authored-By` ou `Generated by`).
3. Toda mutação de estado e validação de invariantes deve ser realizada exclusivamente pelo binário `trustkit`.
4. Os testes no Gate 4 devem cumprir o ciclo TDD mecânico: fase RED (falha comprovada) obrigatoriamente registrada antes da fase GREEN (sucesso comprovado).
5. Abertura de Pull Request ocorre exclusivamente sob demanda explícita do desenvolvedor humano.

## 3. Arquitetura do Workspace

O repositório está estruturado como um Cargo Workspace modular composto por 6 crates especializados:

```
TRustKit/
|-- Cargo.toml
|-- crates/
|   |-- trustkit-core/    # Modelos de domínio, entidades de ciclo de vida (Gates 0 a 6),
|   |                     # interfaces de portas (Ports) e casos de uso de negócio.
|   |-- trustkit-db/      # Camada de persistência SQLite WAL (.trustkit/state.db),
|   |                     # event log imutável, locking e controle de concorrência.
|   |-- trustkit-gh/      # Integração com GitHub CLI / API GraphQL v2 (Projects,
|   |                     # Issues, Pull Requests, comentários e labels).
|   |-- trustkit-ast/     # Análise estática com Tree-sitter (Rust e TypeScript/JavaScript),
|   |                     # contagem de asserções anti-cheat, validação de Mermaid/Gherkin
|   |                     # e Context Slicing para fatiamento de contexto de prompts.
|   |-- trustkit-orch/    # Gerenciador de Git Worktrees efêmeras (reflink / Copy-on-Write),
|   |                     # despacho assíncrono via Tokio e Gauntlet Swarm.
|   +-- trustkit-cli/     # Interface de linha de comando (Clap), modos Humano/Agente
|                         # e servidor Model Context Protocol (MCP).
|-- docs/                 # PRD, ADRs de arquitetura, análises e relatórios de certificação.
+-- specs/                # Especificações executáveis e tarefas atômicas dos ciclos SDD.
```

## 4. Jornada dos 7 Gates do SDD

O ciclo de vida de desenvolvimento é estruturado em 7 portões determinísticos:

```
[Gate 0] Inicialização e Setup de Sessão
    |
[Gate 1] Especificação V2 (spec.md com Mermaid, Gherkin e Rastreabilidade)
    |
[Gate 2] Congelamento Criptográfico da Spec (Selo BLAKE3)
    |
[Gate 3] Decomposição Atômica e Planejamento de Ondas DAG
    |
[Gate 4] Execução Paralela em Git Worktrees + Ciclo TDD Estrito (RED -> GREEN -> REFACTOR / Code Review)
    |
[Gate 5] Gauntlet V2 (Auditoria AST Camada 0 + Swarm de Críticos Camada 1 + Security Review Opcional)
    |
[Gate 6] Certificação Oficial, Security Review Sob Demanda, Merge Determinístico e Pull Request
    |
[Pre-Release] Auditoria Defensiva Global em 6 Fases (trustkit audit security)
```

### Gate 0: Inicialização do Ciclo
Valida credenciais, branches, integridade da árvore de trabalho e inicializa a sessão no banco de estado:
```bash
trustkit init --issue <ISSUE_ID> [--from-prd <CAMINHO_PRD>] [--json]
```

### Gate 1 & 2: Especificação e Congelamento (Spec Lock)
Inicializa o esqueleto da especificação e valida estruturalmente o documento (diagramas Mermaid, cenários Gherkin e fechamento da Matriz de Rastreabilidade RN -> RF -> TASK -> E2E). Ao congelar, gera a assinatura criptográfica via BLAKE3:
```bash
# Inicialização do template de especificação
trustkit spec init --issue <ISSUE_ID> [--json]

# Congelamento e validação de invariantes
trustkit spec lock [--json]
```

### Gate 3: Tarefas Atômicas e Planejamento de Ondas
Valida a pasta de tarefas (`tasks/TASK-NNN.md`), constrói o grafo direcionado acíclico (DAG) de dependências e calcula as ondas de execução topológica:
```bash
trustkit wave plan [--json]
```

### Gate 4: Execução em Git Worktrees, TDD Estrito e Revisão Semântica (Fase Refactor)
Executa tarefas em paralelo criando árvores de trabalho isoladas, fiscaliza a conformidade TDD (`RED -> GREEN`) e incorpora a revisão semântica multi-ângulo na fase `REFACTOR`:
```bash
# Despacha a execução da onda em worktrees isoladas
trustkit wave run --wave <INDICE_ONDA> [--json]

# Registra a fase RED (execução obrigatoriamente falha do teste)
trustkit task test <TASK_ID> --phase red [--json]

# Registra a fase GREEN (execução com sucesso após a implementação)
trustkit task test <TASK_ID> --phase green [--json]

# Executa revisão semântica multi-ângulo na fase REFACTOR (low, medium, high, max)
trustkit task review <TASK_ID> [--effort medium] [--json]

# Conclui e homologa a tarefa atômica (opcionalmente disparando code-review inline)
trustkit task complete <TASK_ID> [--code-review medium] [--json]
```

### Gate 5: Gauntlet Loop V2 e Revisão de Segurança Opcional
Auditoria em duas camadas que protege o repositório contra regressões e violações, acompanhada de revisão especializada de segurança de aplicação (`security-review`) opcional sob decisão do usuário:
- Camada 0 (AST Audit nativo em microssegundos): checagem de anti-cheat em asserções de testes, integridade sintática, ausência de emojis, ausência de trailers IA e detecção de `any` ou `raw.githubusercontent`.
- Camada 1 (Swarm Concorrente): execução de lint, compilação de release, testes E2E com Playwright e críticos de contrato/domínio.
- Camada AppSec Opcional (`security-review`): análise focada no diff da branch em busca de vulnerabilidades exploráveis de alta confiança (`>= 8/10`) com filtragem anti-falso-positivo. Pode ser controlada via flags CLI (`--security-review` ou `--skip-security-review`), prompt interativo TTY (`[s/N]`, padrão `N`) ou política declarativa em `trustkit.toml`.

```bash
# Auditoria de Camada 0 (AST e sintaxe estática)
trustkit gauntlet ast-audit [--json]

# Execução completa da esteira do Gauntlet (com prompt interativo TTY [s/N] se aplicável)
trustkit gauntlet run [--json]

# Execução forçando ou dispensando explicitamente a revisão de segurança do diff
trustkit gauntlet run --security-review [--json]
trustkit gauntlet run --skip-security-review [--json]

# Diagnóstico de falhas e análise de Circuit Breaker
trustkit doctor [--json]
```

Configuração declarativa opcional em `trustkit.toml`:
```toml
[governance.gauntlet]
# Modos: "prompt" (pergunta no terminal), "always" (sempre executa), "disabled" (nunca pergunta)
security_review_mode = "prompt"
min_confidence_threshold = 8
```

### Gate 6: Certificação, Merge e Pull Request
Consolida as evidências em `gauntlet-report.md` (incluindo o status da revisão de segurança ou permitindo executá-la sob demanda caso tenha sido dispensada no Gate 5), executa o merge determinístico para a branch alvo e, sob demanda explícita, abre o Pull Request:
```bash
# Consolida a sessão e gera o relatório final (com suporte às flags de security-review)
trustkit done [--security-review | --skip-security-review] [--json]

# Realiza o merge determinístico para a branch alvo
trustkit merge --target develop [--json]

# Abre o Pull Request (somente sob autorização explícita)
trustkit pr --target develop [--json]
```

### Homologação Pré-Release: Auditoria Defensiva Global (`audit security`)
Para homologação de marcos de versão ou antes de merges em branches estáveis (`staging` ou `main`), o TRustKit oferece um subcomando desacoplado de auditoria defensiva em 6 fases com validação de ledger determinístico (`coverage-ledger.json` e `findings.json`):
```bash
# Executa auditoria global pré-release (perfis: quick, standard, deep)
trustkit audit security [--profile standard] [--scope .] [--output-dir .trustkit/audits/security] [--json]
```

## 5. Recursos Adicionais

### Context Slicing via AST
Permite fatiar cirurgicamente trechos relevantes de código (tipos, structs, funções e contratos) para alimentar os prompts de agentes construtores sem extrapolar limites de tokens:
```bash
trustkit context slice --file <CAMINHO_ARQUIVO> --budget <TOKENS> [--json]
```

### Fast Hooks para Shell e Ferramentas
Intercepta comandos antes e depois da execução em harnesses agênticos:
```bash
trustkit hook pre-tool --command "<COMANDO>" [--json]
```

### Servidor Model Context Protocol (MCP)
Disponibiliza as capacidades de governança e consulta do TRustKit diretamente como ferramentas MCP para IDEs e agentes:
```bash
trustkit mcp
```

## 6. Códigos de Saída Semânticos (POSIX Exit Codes)

O binário `trustkit` retorna códigos de saída determinísticos para permitir que scripts, CI/CD e agentes tratem falhas sem ambiguidade:

| Código | Identificador | Significado |
|---|---|---|
| 0 | CleanPass | Operação concluída com sucesso em conformidade com todos os gates. |
| 1 | InfrastructureBoundaryFault | Falha de infraestrutura: erro de I/O, SQLite, Git ou conectividade de rede. |
| 2 | SpecOrTraceabilityIncomplete | Especificação não congelada, erro de sintaxe Mermaid/Gherkin ou falha de rastreabilidade. |
| 3 | TddLifecycleViolation | Violação do ciclo TDD: tentativa de GREEN sem RED prévio ou omissão de asserções. |
| 4 | AstIntegrityOrInvariantViolation | Violação de invariantes: detecção de emojis, trailers de IA, ciclos no DAG ou adulteração de testes. |
| 5 | CriticSwarmOrPlaywrightFailed | Falha de compilação, linter, reprovação em testes Playwright ou parecer negativo no Gauntlet. |
| 6 | CircuitBreakerTripped | Disjuntor acionado após 5 tentativas consecutivas com falha no Gauntlet. |

## 7. Dual-Audience: Modos de Operação

O `trustkit` foi projetado para atender com ergonomia tanto humanos quanto agentes autônomos:

- Modo Humano (saída padrão em TTY):
  - Interface textual em ASCII puro, sem emojis ou códigos decorativos.
  - Prefixos padronizados: `[GATE-0]` a `[GATE-6]`, `[PASS]`, `[FAIL]`, `[WARN]`, `[INFO]`.
  - Tabelas alinhadas e resumos concisos.

- Modo Agente (`--json` ou via variável de ambiente `TRUSTKIT_AGENT_MODE=1`):
  - Saída em JSON determinístico, sem quebras desnecessárias.
  - Garantia de payload estritamente tipado e livre de campos `null` (arrays vazios `[]` e estruturas de valor padrão).
  - Otimização para consumo direto de tokens no contexto do modelo.

## 8. Compilação e Instalação

### Pré-requisitos
- Rust 1.80+ (edição 2021) e Cargo instalados.
- Git 2.38+ (com suporte a worktrees e sparse-checkout).
- SQLite 3.35+ (suporte nativo a WAL habilitado).
- GitHub CLI (`gh`) autenticado (para interações de Projects/PRs).

### Compilação do Workspace
```bash
# Clonar o repositório
git clone https://github.com/org/TRustKit.git
cd TRustKit

# Compilação em modo de desenvolvimento
cargo build

# Execução da suíte completa de testes
cargo test --workspace

# Compilação para produção com otimizações e LTO
cargo build --release
```

O binário otimizado estará disponível em:
```
target/release/trustkit
```

Recomenda-se adicionar o binário ao `PATH` do sistema ou referenciá-lo diretamente nos scripts de inicialização de workspace.
