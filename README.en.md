# TRustKit

Deterministic Rust Engine for Spec-Driven Development (SDD) Governance, Git Worktree Isolation, and Gauntlet Loop V2.

"True Rust performance for trusted, spec-driven agentic execution."

---

## 1. Overview

TRustKit is a deterministic governance and execution platform built for Spec-Driven Development (SDD) workflows across autonomous coding agents and senior software engineers.

It eliminates the core bottlenecks of purely declarative Markdown skills and legacy interpreted harnesses:
- Drastic latency reduction: replaces 300ms-2,000ms cold-start overhead with native Rust validations executing in 1 to 3 milliseconds.
- Zero compliance hallucination: enforces mechanical verification of syntax rules, test integrity, and project invariants without relying on probabilistic LLM judgment.
- Safe parallelism via Git Worktrees: isolates concurrent builder agents in independent working trees with Copy-on-Write (reflink) support, preventing index corruption and collisions.
- Immutable auditing via Event Sourcing: persists state transitions, command outputs, and artifact digests transactionally in SQLite WAL mode (`.trustkit/state.db`).

### The Hybrid Rust Core + Thin Skill Paradigm

TRustKit adopts a hybrid architecture:
- Declarative Thin Skill: a lightweight Markdown layer in the orchestrator agent's working memory that guides product and code design decisions without invalidating the KV-Cache.
- Native Rust Core: the static `trustkit` binary responsible for 100% of state mutations, AST validation, BLAKE3 cryptographic sealing, Git process orchestration, and GitHub Projects synchronization.

## 2. Mandatory Governance Invariants

All operations managed by TRustKit strictly enforce project integrity rules:
1. Absolute prohibition of Unicode emojis or graphical dingbats in any file, documentation, terminal output, or commit message.
2. Absolute prohibition of AI attribution trailers (such as `Co-Authored-By` or `Generated by`).
3. All state mutations and invariant validations must be performed exclusively by the `trustkit` binary.
4. Tests at Gate 4 must obey the mechanical TDD cycle: the RED phase (proven failure) must be recorded before the GREEN phase (proven pass).
5. Pull Requests are opened exclusively upon explicit human developer command.

## 3. Workspace Architecture

The repository is structured as a modular Cargo Workspace composed of 6 specialized crates:

```
TRustKit/
|-- Cargo.toml
|-- crates/
|   |-- trustkit-core/    # Domain models, lifecycle entities (Gates 0 to 6),
|   |                     # Port traits, and business use cases.
|   |-- trustkit-db/      # SQLite WAL persistence layer (.trustkit/state.db),
|   |                     # immutable event log, locking, and concurrency control.
|   |-- trustkit-gh/      # GitHub CLI / GraphQL API v2 integration (Projects,
|   |                     # Issues, Pull Requests, comments, and labels).
|   |-- trustkit-ast/     # Static analysis via Tree-sitter (Rust and TypeScript/JavaScript),
|   |                     # anti-cheat assertion counting, Mermaid/Gherkin validation,
|   |                     # and Context Slicing for prompt budgets.
|   |-- trustkit-orch/    # Ephemeral Git Worktree manager (reflink / Copy-on-Write),
|   |                     # async dispatch via Tokio, and Gauntlet Swarm.
|   +-- trustkit-cli/     # Command-line interface (Clap), Human/Agent output modes,
|                         # and Model Context Protocol (MCP) server.
|-- docs/                 # PRD, architecture ADRs, research analyses, and certification reports.
+-- specs/                # Executable specifications and atomic tasks for SDD cycles.
```

## 4. The 7-Gate SDD Journey

The development lifecycle is structured across 7 deterministic gates plus pre-release homologation:

```
[Gate 0] Session Initialization and Workspace Setup
    |
[Gate 1] Specification V2 (spec.md with Mermaid, Gherkin, and Traceability)
    |
[Gate 2] Cryptographic Specification Seal (BLAKE3 Digest)
    |
[Gate 3] Atomic Decomposition and Topological DAG Wave Planning
    |
[Gate 4] Parallel Git Worktree Execution + Strict TDD Cycle (RED -> GREEN -> REFACTOR / Code Review)
    |
[Gate 5] Gauntlet V2 (Layer 0 AST Audit + Layer 1 Critic Swarm + Optional Security Review)
    |
[Gate 6] Official Certification, On-Demand Security Review, Deterministic Merge, and Pull Request
    |
[Pre-Release] Global 6-Phase Defensive Security Audit (trustkit audit security)
```

### Gate 0: Cycle Initialization
Validates credentials, branches, working tree cleanliness, and initializes the session in the state database:
```bash
trustkit init --issue <ISSUE_ID> [--from-prd <PRD_PATH>] [--json]
```

### Gate 1 & 2: Specification and Sealing (Spec Lock)
Initializes the specification skeleton and structurally validates the document (Mermaid diagrams, Gherkin scenarios, and full RN -> RF -> TASK -> E2E Traceability Matrix closure). Upon locking, computes a cryptographic BLAKE3 signature:
```bash
# Initialize specification template
trustkit spec init --from-prd <PRD_PATH> [--json]

# Validate invariants and cryptographically lock specification
trustkit spec lock [--json]
```

### Gate 3: Atomic Tasks and Wave Planning
Validates the tasks directory (`tasks/TASK-NNN.md`), constructs the directed acyclic graph (DAG) of dependencies, and computes topological execution waves:
```bash
trustkit wave plan [--json]
```

### Gate 4: Git Worktree Execution, Strict TDD, and Semantic Code Review (Refactor Phase)
Executes tasks in parallel across isolated worktrees, enforces strict TDD compliance (`RED -> GREEN`), and integrates multi-angle semantic code review into the `REFACTOR` phase:
```bash
# Dispatch wave execution in isolated worktrees
trustkit wave run --wave <WAVE_INDEX> [--json]

# Record RED phase (test execution must fail)
trustkit task test <TASK_ID> --phase red [--json]

# Record GREEN phase (test execution must pass after implementation)
trustkit task test <TASK_ID> --phase green [--json]

# Run multi-angle semantic code review in the REFACTOR phase (low, medium, high, max)
trustkit task review <TASK_ID> [--effort medium] [--json]

# Complete and homologate the atomic task (optionally triggering inline code-review)
trustkit task complete <TASK_ID> [--code-review medium] [--json]
```

### Gate 5: Gauntlet Loop V2 and Optional Security Review
Two-layer verification pipeline protecting the repository against regressions and invariant violations, paired with an optional user-governed application security diff review (`security-review`):
- Layer 0 (Native Microsecond AST Audit): anti-cheat test assertion checks, syntactic integrity, zero emojis, zero AI trailers, and detection of forbidden `any` or `raw.githubusercontent` patterns.
- Layer 1 (Concurrent Critic Swarm): linter execution, release build check, Playwright E2E tests, and domain/contract critics.
- Optional AppSec Layer (`security-review`): branch diff security analysis targeting high-confidence exploitable vulnerabilities (`>= 8/10`) with anti-false-positive filtering. Controlled via CLI flags (`--security-review` or `--skip-security-review`), interactive TTY prompt (`[s/N]`, default `N`), or declarative policy in `trustkit.toml`.

```bash
# Layer 0 audit (AST and static syntax)
trustkit gauntlet ast-audit [--json]

# Full Gauntlet execution (prompts [s/N] on interactive TTY when applicable)
trustkit gauntlet run [--json]

# Explicitly force or skip the specialized branch diff security review
trustkit gauntlet run --security-review [--json]
trustkit gauntlet run --skip-security-review [--json]

# Diagnose failures and inspect Circuit Breaker state
trustkit doctor [--json]
```

Optional declarative configuration in `trustkit.toml`:
```toml
[governance.gauntlet]
# Modes: "prompt" (interactive terminal prompt), "always" (always run), "disabled" (never prompt)
security_review_mode = "prompt"
min_confidence_threshold = 8
```

### Gate 6: Certification, Merge, and Pull Request
Consolidates verification evidence into `gauntlet-report.md` (recording the security review status or allowing on-demand execution if skipped at Gate 5), performs a deterministic merge into the target branch, and opens a Pull Request upon explicit command:
```bash
# Certify session and compile final report (supports security-review flags)
trustkit done [--security-review | --skip-security-review] [--json]

# Perform deterministic merge into target branch
trustkit merge --target develop [--json]

# Open Pull Request (human-triggered only)
trustkit pr --target develop [--json]
```

### Pre-Release Homologation: Global Defensive Security Audit (`audit security`)
For release milestones or before merging into stable branches (`staging` or `main`), TRustKit provides a decoupled 6-phase defensive security audit subcommand with deterministic ledger validation (`coverage-ledger.json` and `findings.json`):
```bash
# Execute global pre-release security audit (profiles: quick, standard, deep)
trustkit audit security [--profile standard] [--scope .] [--output-dir .trustkit/audits/security] [--json]
```

## 5. Additional Capabilities

### AST Context Slicing
Surgically slices relevant code structures (types, structs, functions, and contracts) to feed builder agent prompts within strict token budgets:
```bash
trustkit context slice --file <FILE_PATH> --budget <TOKENS> [--json]
```

### Fast Shell and Tool Hooks
Intercepts shell commands before execution in agentic harnesses:
```bash
trustkit hook pre-tool --command "<COMMAND>" [--json]
```

### Model Context Protocol (MCP) Server
Exposes TRustKit governance and query capabilities directly as MCP tools for IDEs and agents:
```bash
trustkit mcp serve
```

## 6. Semantic POSIX Exit Codes

The `trustkit` binary returns deterministic exit codes so CI/CD pipelines and autonomous agents can handle failures unambiguously:

| Code | Identifier | Meaning |
|---|---|---|
| 0 | CleanPass | Operation completed successfully in compliance with all gates. |
| 1 | InfrastructureBoundaryFault | Infrastructure failure: I/O, SQLite, Git, or network connectivity error. |
| 2 | SpecOrTraceabilityIncomplete | Unsealed specification, Mermaid/Gherkin syntax error, or broken traceability. |
| 3 | TddLifecycleViolation | TDD lifecycle violation: GREEN attempted without prior RED or missing assertions. |
| 4 | AstIntegrityOrInvariantViolation | Invariant violation: emojis, AI trailers, DAG cycles, or test tampering detected. |
| 5 | CriticSwarmOrPlaywrightFailed | Build failure, linter error, Playwright test failure, or negative Gauntlet verdict. |
| 6 | CircuitBreakerTripped | Circuit breaker tripped after 5 consecutive failed Gauntlet attempts. |

## 7. Dual-Audience Operation Modes

`trustkit` is designed for both human developers and autonomous agents:

- Human Mode (default TTY output):
  - Pure ASCII text interface with zero emojis or decorative dingbats.
  - Standardized prefixes: `[GATE-0]` through `[GATE-6]`, `[PASS]`, `[FAIL]`, `[WARN]`, `[INFO]`.
  - Aligned tables and concise diagnostic summaries.

- Agent Mode (`--json` or via `TRUSTKIT_AGENT_MODE=1`):
  - Deterministic single-line JSON output.
  - Strictly typed, null-free payload guarantee (empty arrays `[]` and explicit default values).
  - Optimized for direct token consumption in model context windows.

## 8. Building and Installation

### Prerequisites
- Rust 1.80+ (2021 edition) and Cargo.
- Git 2.38+ (with worktree and sparse-checkout support).
- SQLite 3.35+ (native WAL support enabled).
- Authenticated GitHub CLI (`gh`) for Projects/PR synchronization.

### Workspace Compilation
```bash
# Clone the repository
git clone https://github.com/org/TRustKit.git
cd TRustKit

# Development build
cargo build

# Run full workspace test suite
cargo test --workspace

# Production build with optimizations and LTO
cargo build --release
```

The optimized binary will be available at:
```
target/release/trustkit
```
